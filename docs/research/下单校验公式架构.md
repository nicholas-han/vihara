# 交易所保证金校验与风控：架构方案与产研协同机制

> 主题：下单保证金校验、实时风控监测该不该用规则引擎；逻辑写入代码后，如何解决"产品维护文档难、产研对逻辑理解不一致"的问题。
>
> 核心结论一句话：**逻辑用代码、参数用配置、案例做规格、轨迹做文档**。

---

## 1. 业务场景

1. **下单前置校验（含保证金校验）**：计算客户已有仓位的保证金占用、现金余额、新订单的保证金占用；按账户类型、保证金模式（全仓/逐仓）、品种类型（现货/期货/期权）分派不同的计算方式，相互交织。
2. **实时风控监测**：随行情盯市，持续计算账户保证金率，判断是否触及警戒线/追保线/强平线，触发相应动作。

---

## 2. 核心架构决策：代码，而不是规则引擎

### 2.1 保证金校验的本质是"计算"，不是"规则"

保证金校验是一条算术流水线：

```
账户快照 + 新订单
  → 逐仓位计算占用（期货按档位费率，期权按情景法/组合保证金）
  → 按保证金模式聚合（全仓轧差 / 逐仓独立）
  → 计算可用余额
  → 比较：可用 ≥ 新订单初始保证金？
```

规则引擎（Drools 类产生式系统）擅长**无序、扁平、经常增删的组合谓词判定**，不擅长**数值计算链**：中间量传递别扭、求值顺序靠优先级隐式控制、精度处理麻烦，最终会变成"用最难调试的方式写代码"。

"账户类型 × 保证金模式 × 品种类型"的交织是**结构化的多维分派**，不是任意规则。用策略组合表达最清晰：

- 每个品种一个保证金计算器（现货 / 期货 / 期权）；
- 每种保证金模式一个聚合器（全仓 / 逐仓）；
- 账户类型决定参数集和允许的组合。

放进规则引擎反而是降维：把有清晰结构的分派打散成无序规则汤，再引入规则冲突、触发顺序、优先级等引擎自带的复杂度。

### 2.2 三个硬约束

| 约束 | 说明 | 对规则引擎的影响 |
| --- | --- | --- |
| **延迟** | 前置校验在交易热路径上，预算为微秒到个位毫秒 | RETE 求值、对象装配、GC 压力不可接受 |
| **确定性与可审计** | 监管与客诉要求精确复现"为什么拒单/为什么强平" | 版本化代码+参数可重放复现；规则引擎要回答"当时哪些规则以什么顺序触发"，审计更难 |
| **一致性（最大的坑）** | 保证金数学至少有三个消费者：前置校验、实时监测、强平引擎，**必须共用同一份计算库** | 一处代码一处规则引擎 ⇒ 两边算出的保证金率有一分钱出入，就会出现"能下的单立刻告警"或"该爆的仓没爆" |

### 2.3 逻辑与参数分离

规则引擎的卖点是"业务人员不发版改规则"，但没有交易所敢让风控绕过工程评审热改保证金**公式**。真正高频变化的是**参数**：

- 保证金档位表（仓位价值 → 费率/杠杆上限）
- 各品种风险参数（费率、涨跌停带、持仓上限）
- 账户等级 → 杠杆倍数
- 爆仓线/警戒线阈值

**做法：计算引擎用代码写死；参数外置为可热加载、带版本、带生效时间的配置表。** 这拿到了规则引擎承诺的灵活性，不付它的代价。

前置校验组织成**校验管道**：参数合法性 → 余额 → 保证金 → 持仓限额 → 价格带 → 自成交防范……每个校验是实现同一接口的代码模块，管道的启停与顺序由配置决定。新增校验 = 加一个模块 + 改一行配置。

### 2.4 实时风控监测：事件驱动重算，不是规则匹配

```
标记价格更新 / 账户权益变动
  → 增量重算受影响账户的保证金率（复用同一计算库）
  → 与阈值序列比较（警戒 → 追保 → 强平）
  → 越线触发动作（通知 / 限开仓 / 强平）
```

难点在增量计算性能（一次价格跳动可能影响大量账户）和与强平引擎的衔接；"规则"只是最后的阈值比较。规则引擎解决的是它最不难的 5%。

### 2.5 规则引擎的合理位置

**异步、延迟不敏感、组合判定型、由运营/风控频繁调整**的场景：

- 反欺诈/异常行为标记（"新注册 + 大额入金 + 立即满杠杆 → 打标人工审核"）
- 提币审核触发条件
- 运营侧监控告警

即便在这里，流处理 + 轻量表达式引擎（CEL / Aviator 类，一条规则 = 一条可配置布尔表达式）通常也比重型规则引擎清爽。

### 2.6 分场景结论

| 场景 | 形态 | 方案 |
| --- | --- | --- |
| 下单保证金校验 | 热路径数值计算 | 代码（策略组合 + 校验管道），参数外置 |
| 实时监测 / 爆仓 | 事件驱动增量重算 | 代码，与前置校验共用同一计算库 |
| 反欺诈 / 审核 / 告警 | 异步组合谓词，频繁调整 | 表达式引擎或轻量规则配置 |

**速记判断准则：一条"规则"里含有算术，它就不该进规则引擎。**

## 3. 计算库的四个地基性质

后续所有产研协同机制都建立在这四条之上：

1. **纯函数**：输出完全由（账户快照、订单、参数版本）决定；计算过程中不查库、不读实时行情，所有输入在进入计算前收进快照对象。
2. **输入可快照**：账户快照 + 订单 + 参数版本可序列化存档（审计本来就需要）。
3. **参数版本化**：档位表等参数带版本号与生效时间，重放时取"当时那个版本"。
4. **可插拔轨迹收集器**：计算过程接受一个 trace 收集器参数；生产热路径传空实现（零成本），解释/测试场景传真实现。

有了 1+2，**任何历史决策都可以重放**；有了 4，重放时可以拿到完整计算轨迹。

## 4. 产研单一真相机制

### 4.1 问题本质

"产品文档和代码对不上"不是文档格式问题，而是**两份真相问题**：逻辑在代码里活着、在文档里死着，两者没有机制强制同步，漂移是必然的。解法不是写更好的 prose，而是**换一个产研共享、且机器可强制校验的载体**：

- 产品写公式和文字描述必然有歧义；**产品给具体案例是无歧义的**。
- 产品提供**事实**（案例、参数、预期值），研发提供**逻辑**（代码），机器（CI）负责证明两者一致。这个分工是稳定的。

### 4.2 机制一：案例表即规格（executable specification）

产品维护案例表（Excel/CSV 均可）：

| 案例 | 账户类型 | 模式 | 已有仓位 | 余额 | 新订单 | 预期结果 | 预期占用 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| C-041 | 普通 | 逐仓 | … | 500 | … | 拒绝 | — |
| C-042 | 专业 | 全仓 | … | 500 | … | 通过 | 312.5 |

案例表**直接灌入 CI（持续集成）作为 golden test**：每次代码提交自动重跑全表，任何一行实际输出 ≠ 预期值即无法合入。效果：

- 产研理解分歧以"一个失败案例"的形式浮出，讨论从"我理解的逻辑是…"变成"C-042 该输出多少"——有唯一答案，谈完即固化；
- 新需求的验收标准 = 新增案例行，需求文档与测试用例合一；
- 文档不会烂：烂了 CI 就红。

**覆盖分层**（控制产品工作量的关键）：

| 层 | 负责人 | 内容 | 目标 |
| --- | --- | --- | --- |
| 业务案例层 | 产品 | 代表性案例 + 边界案例（压线、跨档、精度舍入、爆仓瞬间下单） | 每条业务规则至少有案例钉住 |
| 性质测试层 | 研发 | 不变量 + 随机输入轰炸（property-based testing），如"仓位加大占用单调不减""全仓总占用 ≤ 各仓逐仓之和" | 数学上不出鬼、穷举覆盖 |

**维护工作流**（公式变更时）：

1. 不手工重算预期值——工具用新代码全量重跑案例，产出"预期值变更报告"：哪些案例变了 + 每个变化的轨迹 diff（变在哪一步一目了然）；
2. 产品审阅 diff，逐个或批量确认，确认后新值自动写回案例表；
3. **防橡皮图章**：关键边界案例保留"双录"——产品独立算出预期值填入，不接受机器生成值；普通案例走批量确认，边界案例走独立核算；
4. **从生产流量捞案例**：定期采样真实订单输入，重放后由产品确认预期，沉淀入库。真实流量踩到的边界比人凭空想的更刁钻。

### 4.3 机制二：计算轨迹即活文档

**思路**：计算引擎在算出结果的同时，顺手产出一份结构化"草稿纸"。它不描述逻辑，它**就是**逻辑本身——代码变了输出自动跟着变，不存在过期。

**轨迹数据模板**（无行业统一标准，但可直接借 OpenTelemetry span 树的形状；节点 schema 定一次即稳定）：

```jsonc
{
  "step": "position_margin",              // 步骤 id（来自稳定的步骤词汇表）
  "title": "仓位占用保证金",                // 渲染用名称
  "inputs": { "symbol": "BTC-PERP", "notional": 58000 },
  "params": { "table": "margin_tiers", "version": "v47", "row": "tier1" },
  "rule": "notional × tier_rate",          // 公式/规则标识
  "output": { "margin": 290 },
  "children": [ /* 子步骤 */ ]
}
```

渲染后的样子（示意）：

```
可用保证金校验 → 拒绝
├─ 账户权益 = 380
│  ├─ 现金余额 = 500
│  └─ 未实现盈亏 = -120（标记价 58000，快照 v20260703-1421）
├─ 已有仓位总占用 = 375（全仓轧差）
│  ├─ BTC-PERP：名义 58000 × 费率 0.5% = 290（档位表 v47，第 1 档）
│  └─ ETH-PERP：… = 85
├─ 可用 = 380 − 375 = 5
└─ 新订单初始保证金 = 312.5 > 5 → 不足
```

**关键设计点**：

1. **数据与渲染分离**：引擎只产出结构化树（JSON）；渲染是另一层——内部工具渲染中文可读文本、审计存原始 JSON、CI 失败时 diff 两棵树，同一份数据多种视图。
2. **收集器 = Builder + Null Object 模式**：接口约三五个方法（`beginStep(id, inputs)` / `endStep(output)` / `refParam(...)`），真实现建树，空实现零成本（生产热路径用）。API 形状可照 OpenTelemetry tracer 设计。
3. **重放式解释（最优雅的一点）**：因为计算是纯函数，**交易时不记轨迹，只记输入**（快照+订单+参数版本，审计本来就要存）。有人问"为什么"时，取出当时输入、开着 trace 重跑一遍，轨迹当场生成。交易时零成本，解释时按需付费，且永远与真实逻辑一致。
4. **步骤词汇表是唯一需要产研共同设计的部分**：计算分成哪些步骤、每步叫什么（"权益折算""档位查表""全仓轧差"…）。没有模板可抄——它就是业务本身；但也是最有价值的设计产出：产研说话从此有共同坐标系（很多"理解不一致"其实是同一个词指不同东西，轨迹把每个词钉在一个具体计算步骤上）。步骤 id 一旦定下不轻易改，案例 diff、审计存档、客服话术都会引用它。

**呈现层：一个薄的内部小工具**

- **构造模式**：网页表单手填场景（账户状态、仓位、新订单）→ 调计算库（开 trace）→ 渲染轨迹树。产品自助验证理解、设计新需求边界案例。
- **回查模式**：输入真实订单号 → 拉取当时输入快照重放 → 给客服、风控排查用。
- CI 案例失败的 diff 报告复用同一渲染器。
- **可见性分级**（需要认真设计的唯一一点）：产品/风控看全量；客服看脱敏简化版；终端客户只能看到结论级字段（如"可用保证金不足"），绝不泄露内部风险参数。

### 4.4 机制三：参数表与决策表共管

- **参数表**（档位、费率、阈值）本来就是外置配置：让产品直接查看、甚至直接提变更（走审批流生效）。产品眼中"保证金规则"的很大一部分就是这些表，而表就是生产在跑的东西——天然无文档漂移。
- **决策表**（账户类型 × 模式 × 品种 → 用哪个计算器、允许什么组合）整理成表放进代码仓库，用一个测试断言"代码行为与表一致"。产品看表，机器保证表是真的。

### 4.5 机制四：流程闸门

规格物（案例表、决策表、参数表）**与代码同仓库、同 PR 变更**：改逻辑的 PR 必须携带对应案例行的变更，且产品在 PR 上确认过预期值方可合入。把"文档更新"从自觉变成流程卡点，成本≈0。

### 4.6 两个不建议的方向

- **不要让产品读代码**，也不要把代码写成伪自然语言——两边都别扭。
- **不要发明"产品能写逻辑"的 DSL**——等于让产品在没有类型检查、测试、code review 的条件下写代码；分歧不会消失，只会变成没人会调试的 bug。

---

## 5. 落地顺序建议

1. **地基**：把保证金计算收敛成纯函数计算库（快照输入、参数版本化）——前置校验、实时监测、强平三处共用。这一步价值最大，也是后面一切的前提。
2. **参数外置**：档位/费率/阈值进配置中心，带版本与生效时间。
3. **案例表 + CI**：产品先从最有争议的边界场景开始建案例，研发补性质测试。
4. **轨迹收集器**：定步骤词汇表 → 定节点 schema → 计算库埋点（空实现兜底热路径）。
5. **重放与小工具**：输入存档 → 重放服务 → 内部网页（构造/回查两模式）→ 可见性分级。
6. **流程闸门**：规格物入仓库、同 PR、产品确认。

---

## 6. 速记

- 保证金校验是**计算**不是规则；含算术的"规则"不进规则引擎。
- **逻辑用代码、参数用配置**；热路径 = 代码，异步扁平判定 = 才轮到规则引擎。
- 三个消费者（前置校验/实时监测/强平）**共用同一计算库**，否则必出一致性事故。
- 产研对齐靠**案例约束代码**，不靠"文档描述代码"：案例表进 CI、引擎带 explain、参数表共管、规格与代码同 PR。
- 纯函数 + 输入快照 + 参数版本 ⇒ **重放**；重放 + 可插拔收集器 ⇒ **零成本的活文档**。
