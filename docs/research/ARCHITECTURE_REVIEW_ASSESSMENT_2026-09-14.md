## 3. 应当保留的基础

**会计账本与持仓账本共同提交。** 一笔交易涉及现金、证券和成本，当前同一事务保存，出错一起回滚。把它们拆成独立服务会增加协调成本。命令还包含稳定请求键、重试回执和保存点，见 [统一命令](../../ledger/ledger/investment/application/service.py#L334)。

**正式账本是唯一入账入口。** 导入通过同一个命令服务，来源链接和正式交易一起提交。Ledger 内部传递数据库连接是为了共享事务，不应误判为页面绕过账本。预览在临时一致性快照中执行，确认时检查预览是否过期，见 [导入提交与预览](../../ledger/ledger/investment/imports/service.py#L597)。

**主数据、历史记账依据和市场估值已区分。** 证券定义归 IM；记账效果归 Ledger；行情估值归 Portfolio。主数据经济字段有引用指纹保护，避免悄悄改变既有账本解释；Book FX 与 Market FX 也没有混用。这些原则值得继续强化。

**研究、预测、券商连接、订单编排已有小接口。** Forecaster 的 `fit/predict`、回测的 Clock/MarketData/Execution、订单编排对 BrokerGateway 的调用，是合理的分工。重型研究依赖可选安装，也没有必要把每个预测方法再拆成一个模块。

**测试包含真实的边界行为。** 例如 [独立运行测试](../../ledger/tests/test_investment_boundary.py#L9) 阻止 Ledger 加载 Portfolio/FastAPI；导入测试验证重复、过期预览、故障回滚；账本测试覆盖并发支出和历史冻结结果。后续应扩展这种有业务意义的契约测试。

## 4. 为什么现在值得 Review

### 4.1 历史导入的完整性管理先由新 PRD 决定

**性质：已确认的能力缺口，直接影响下一步功能。**

当前 [import_batches](../../ledger/ledger/investment/persistence/006_imports.sql#L1) 只有批次 ID、文件名、文件内容哈希。行中保留原始内容、当前映射和状态，正式链接也保存了去重及内容指纹，因此已有来源追溯基础；但还没有成体系的结单账户/期间、文档身份与定位、解析运行版本、修改历史、期间完整度和对外部结单的核对结论。新的历史导入 PRD 将部分定义这些能力。

在当前实现下，能查询“某行是否入账”，却不能系统回答：

- 某账户 2020–2026 哪些月份资料齐全，哪些尚未收到，哪些只核对了一部分？
- 同一日结单 CSV、PDF、月结单及修订版，哪些是重复证据，哪些包含新事实？
- 正式交易来自原文件哪一行或哪一页，用了哪版解析与映射规则？
- 修改解析器后，哪些待处理行可以重算，哪些已入账内容需要发起纠错？
- 期末现金、持仓、费用汇总与券商结单是否一致，差异是否已解释？

账本内部借贷平衡、持仓一致性校验，不能证明外部结单没有遗漏。即使漏了一整笔交易，内部账也可能保持平衡。

当前行动建议是：先完成新的历史导入 PRD，再以 PRD 的验收范围重新评估上述问题还剩多少；不必等实现完成才评估，也不强制 PRD 覆盖上面所有问题。来源分组和审核状态以新 PRD 为准，不自动成为新的 canonical 交易分组或改变已确认费用规则。缺口只有在影响首期实际使用时才补。

### 4.2 历史补录流程暂不作为当前建设范围；未来录入校验仍需明确

**性质：现有保护规则带来的产品约束，不是已经发现的记账错误。**

当前单批次按生效日期、文件行号排序；账本同日按正式交易 ID 排序。后补的同日记录排在后面。若补录改变旧交易已经冻结的现金成本或卖出选批，会拒绝并返回受影响交易，见 [排序](../../ledger/ledger/investment/imports/service.py#L495)、[回放保护](../../ledger/ledger/investment/application/service.py#L215) 和 [当前设计](../projects/portfolio-holdings/design/TECHNICAL_DESIGN.md#L187)。

项目计划在正式启用前确保历史记录是完整版本，因此这类“正式使用后补录多年旧记录”的流程暂不列为当前交付目标。跨账户转账仍会把影响传到另一个账户，不能简单认为各账户文件夹可完全独立入账；这条规则会保留在未来日常录入的校验设计中。

本轮不新增历史补录、重排或长期人工纠错的产品流程，也不改变现有冻结结果保护。历史初始化如何执行以新 PRD 为准。系统正式启用前，再针对未来每日/每周的新交易核对日期、余额、来源身份、重复和冲销规则；已有校验复用，不重复建设。

### 4.3 有经济历史后的升级策略尚需补齐

**性质：已确认的版本转换范围限制。**

当前 v8 准备工具只接受 v7 的参考数据。发现经济记录或 staging 历史就返回 `LEGACY_CONVERSION_REQUIRED`，见 [准备器](../../ledger/ledger/investment/persistence/prepare_v8.py#L79)；运行中的 Store 也不会自动迁移不匹配版本。

这种明确拒绝有保护价值，但不能当作以后每次变更数据结构都已有完整迁移能力。它与 CSV/PDF 大小无关，是未来修改程序时如何保留已有账本的问题。当前只保留一条工程约定：以后每次涉及正式库结构或经济语义变更，在该次改动中准备备份、转换、前后核对和恢复方式。不提前建设通用升级平台，也不把未来迁移功能设为当前 PRD 的前置任务。

### 4.4 导入规模已有可观察的增长成本，但暂不需要过度优化

**性质：已测得的扩展风险；尚非真实多年交易的容量结论。**

现有导入每个来源组调用统一命令，统一命令会重新检查全历史。完整性保护正确，但反复从头扫描会使总工作量接近平方增长。列表目前还固定最多返回最近 100 批，没有分页，见 [列表](../../ledger/ledger/investment/imports/service.py#L431)。

本次在临时空账本分别导入同一天、同账户、每行 1 HKD 的模拟入金，采用现有 upload → preview → canonicalize。实验使用的 `source_id` 不是系统识别的 `external_transaction_id` 字段，实际采用文件哈希/行身份后备去重；表中耗时仍来自实际执行，但不能称作外部交易 ID 路径的测试：

| 行数 | 预览耗时 | 提交耗时 | 结果 |
|---|---:|---:|---|
| 100 | 0.21 秒 | 0.21 秒 | 100 笔成功 |
| 500 | 4.28 秒 | 4.30 秒 | 500 笔成功 |
| 1,000 | 22.17 秒 | 23.09 秒 | 1,000 笔成功 |

这是同机单次、简单现金事件的探索性测试；环境中还有其他评估工作，不是标准基准，也不能直接外推七年数据耗时。测量没有 PDF 提取/OCR，主要反映规范 CSV 进入账本时的历史检查成本。

一次性初始化慢一些可以接受，当前不安排性能架构改造。但即使日常只新增少量记录，单次提交仍读取既有历史；增量小不完全消除成本。历史初始化完成后，用一份独立副本验证一次“日常一日或一周新增”的耗时即可，能接受就停止优化。实测影响使用时再做局部改进，保留原子提交、历史效果检查和去重。

### 4.5 单向依赖已经成立，公开接口可收窄（本轮已实施）

**性质：已确认的实现耦合，当前并非架构违规。**

评估时，Portfolio API 直接使用 Ledger 的 `persistence.Store`、`ChargeReferences`、查询函数及数据库连接；行情模块在共用数据库中管理行情表，并直接读取 `accounting_config`。9 月 15 日已将 [API](../../portfolio_manager/portfolio_manager/holdings/api.py) 路由切换到公开 Commands/Queries/References/Imports；行情 SQL 收到 [MarketRepository](../../portfolio_manager/portfolio_manager/holdings/integrations/market.py)，估值只消费余额和快照，功能币经 Queries 获取。Store 和具体 catalog 在启动组合层构造。

现有文档说明了行情表物理共库安排，因此不是“发现跨模块 SQL 就判错”。但以后存储布局或查询内部结构变化，会直接影响上层功能。宜明确公开的命令、查询、参考数据及行情访问接口，以及哪些内部入口不再供外部调用；传递有定义的数据对象，而不是让新增功能继续依赖连接和表结构。建议的最小 `ReferencePort` 与解析 DTO 见 [跨模块主数据与参考接口最小合同](CROSS_MODULE_REFERENCE_CONTRACT_2026-09-15.md)。

`Service` 接近 1,000 行、导入服务约 765 行，提示其责任正在增长，但不是拆分依据。应沿“业务规则、来源转换、工作流、查询”分清职责，而非按文件长度切碎。

### 4.6 主数据多个投影的可复现差异（本轮已修复）

**性质：确定的接口缺口；当前 Holdings 的直接 JSON 读取路径不受这个复现影响。**

HoldingCatalog 的标识符支持供应商/来源 `authority` 和有效期，解析时按两者筛选，见 [目录实现](../../instrument_manager/instrument_manager/holding_catalog.py)。评估基线的派生 SQLite 索引不保存 authority，唯一键也不包含有效期。9 月 15 日已修复 [索引实现](../../instrument_manager/instrument_manager/index/sqlite_index.py)：保留来源、起止日期和目标身份，允许不连续有效期；在临时文件构建和校验后原子替换，失败保留旧索引。

评估阶段临时数据复现：给同一产品设置两个不同来源、互不重叠期间的相同 TICKER。真实 C++ 加载和 HoldingCatalog 均接受，按对应日期/来源解析成功；重建 SQLite 索引却报唯一约束冲突。该场景现已纳入回归并通过。这也说明只看既有测试通过，仍可能漏掉跨接口组合。

还需区分：按日期解析证券代码、用经济指纹保护历史引用、按历史版本读取完整证券定义，是三种不同能力。当前 HoldingCatalog 的 `fingerprint` 保护的是 Holdings 所需经济核心字段，不等于完整主数据历史版本系统；本轮未修改该算法。

本轮最小修复和后置范围见 [接口合同](CROSS_MODULE_REFERENCE_CONTRACT_2026-09-15.md)。当前没有完整 SQLite resolver，未来有消费者时再复用解析逻辑并验证两条路径一致。将来增加复杂合约、公司行动和历史估值时，再按业务需要扩展版本语义；不必现在建设一个万能主数据平台。

### 4.7 研究、真实执行与正式账本需要显式转换合同

**性质：当前待接入的业务链，不能当作已建成功能的失败。**

研究 [Order/Fill](../../portfolio_manager/portfolio_manager/strategy/base.py#L15) 是目标仓位、浮点数和模拟费用；[Plumber 模型](../../plumber/plumber/models.py#L33) 表达真实订单/成交、Decimal 和状态；正式 Ledger 使用账户、PositionScope、Product/Listing 和日期等字段，费用按独立事件表达。成交接入还需约定稳定来源；手工命令并不要求来源字段，导入缺少外部 ID 时也可使用文件哈希等后备身份。这些模型各有用途，不能因为同名就简单合并。

回测循环目前同步执行后立即应用成交，见 [回测引擎](../../portfolio_manager/portfolio_manager/engine/engine.py#L33)；真实异步订单的持久化与恢复在另一套订单运行时中实现。文档中的回测/实盘共享目标，还需要真实的订单生命周期合同才能实现。

此外，Hyperliquid 文档明确采用券商专用响应，并未承诺实现 Futu 所用 Gateway，见 [接入边界](../modules/plumber/HYPERLIQUID.md#L71)。此处应保留差异，等具体产品需要再提取最小通用接口。

当前可先规定未来“成交 → 规范事件 → Ledger”的通道，历史导入与实盘成交沿用同一套入账约束：稳定身份、账户映射、按时点识别标的、时区、精度、独立费用和幂等来源。实际接入可以后置。

### 4.8 文档与持续验证也属于架构建设

**性质：部分确定冲突，以及工程保障缺口。**

## 5. 建议收口的职责表

下表是建议方向，供后续设计使用；保留现有模块，不预先决定增加顶层包或拆数据库。

| 概念/能力 | 建议主要维护方 | 需要明确的跨模块合同 |
|---|---|---|
| Product / Observable / Listing、标识符和有效期 | Instrument Manager | 稳定 ID、按日期/来源解析、经济定义版本、各投影一致性 |
| Financial Account / PositionScope、正式交易和记账结果 | Investment Ledger | 唯一命令入口、金额精度、错误、幂等、冲销与历史查询语义 |
| 来源结单、解析运行、待处理差异、期间完整度 | 以正在编写的新 PRD 为准，不提前决定包结构 | 对照 PRD 已覆盖内容后评估缺口，复用 Ledger imports；不增加一次性历史补录工作流 |
| 对外部结单的核对 | 若新 PRD 需要，由其应用协调，Ledger 提供只读结果 | 核对口径和结论以 PRD 为准，剩余完整性功能可后置 |
| 页面、导入操作、组合分析和估值展示 | Portfolio Manager | 消费命令/查询合同，避免新增页面直接访问账本内部 SQL |
| 行情数据 | 当前 Portfolio 行情接口；以后有多个消费者再考虑独立模块 | 价格/FX 单位、来源、观察时间、可见时间；保留 Market FX 与 Book FX 区分 |
| 券商连接与券商原始响应 | Plumber | 账号环境、标的代码、订单/成交身份、状态及时间 |
| 持久订单编排与恢复 | Customized Orders | 指令幂等、未知结果处理、成交发布/查询和恢复 |
| 预测、研究回测 | Forecaster / Portfolio 回测 / Strategies | 时间一致性、数据可见性、合成标的、目标仓位到真实订单的转换 |
| 定价计算 | Asset Pricer | 合约投影、单位、输入市场数据、能力不支持时的明确结果 |

例如 statements 文件夹可以继续用 `account_code` 命名，但导入工作区内部宜关联稳定 `financial_account_id`。可修改的目录名和证券 ticker 都不应自动成为永久业务身份。

## 6. 按当前反馈调整后的推进顺序

| 阶段 | 应形成的结果 | 何时算完成 |
|---|---|---|
| 1：现在修正文档并实施最小接口 | 已修正文档、IM 投影差异，接入 ReferencePort/Ledger 公开入口并分离估值读取；见 [接口设计与实施范围](CROSS_MODULE_REFERENCE_CONTRACT_2026-09-15.md) | 已通过公开业务场景、全仓库回归和独立审查；当前实现、历史背景、未实施建议分开 |
| 2：PRD 定稿后对照范围 | 重新评估 4.1 缺口，确认新功能要调用哪些现有模块 | 不强制补齐全部完整性能力，不增加历史补录产品流程 |
| 3：按 PRD 开发实际功能 | 复用本轮公开入口；新增用例需要时小步扩展接口，其余旧路径在实际触及时迁移 | 数据身份、费用规则、经济指纹和原子事务保持一致；按 PRD 验收，不扩成全系统重写 |
| 4：正式启用前验证日常录入 | 复用并梳理日期、余额/持仓、重复、歧义、预览过期和冲销校验；用历史完整的副本试一次每日/每周增量 | 结果正确、耗时可接受即可；没有实测需求就不做性能优化 |
| 5：每轮新业务做局部 review | 实盘成交、更多券商或新产品开始接入时，检查其触及的接口；结构变更在对应改动内处理数据升级 | 接受未来增量重构，避免提前预测所有接口或建设通用升级框架 |

上述顺序允许文档/接口实施与新 PRD 并行，避免相互等待。本轮最小改进已经完成，更深入的接口扩展按新 PRD 的实际调用范围逐步推进。

以下工作目前收益不足：为了独立部署而拆微服务；预建通用事件总线、工作流平台或插件框架；把所有 Account/Order/Instrument 强行合成万能模型；把 Forecasting 的每类算法拆成模块；为 planned matching/risk/clearing 创建空框架；仅为更换前端技术而重写页面。

Review 的结束标准应是下一轮开发有可信的职责、接口和数据生命周期规则，并能通过代表性跨模块场景验证。模块数量、图的复杂度和改动代码行数都不应作为成果指标。

## 7. 对项目负责人的建议

现在做一次有范围的梳理仍有必要，时间点也合适：Financial Account 和独立 Investment Charge 已经落地，新的历史导入 PRD 正在形成，主数据投影和文档冲突也已被确认。范围应收敛到“避免当前 PRD 建在不稳定边界上”；历史完整性剩余部分等 PRD 完成后再评估，一次性性能也只做足够的容量验证。

技术上的包组织、接口形式、测试和迁移实现可由开发侧负责。项目负责人主要决定业务问题：怎样才算某一期间资料完整、无法解释的差异如何处理、哪些历史产品纳入首期、允许哪种纠错流程，以及哪些记录确认后才能正式入账。无需先掌握架构术语再作判断。
